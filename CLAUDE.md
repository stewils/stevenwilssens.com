# steven.wilssens.com

Steven Wilssens's resume site, read mostly by recruiters and hiring managers. React + TypeScript + Vite, prerendered to static HTML on Cloudflare Pages, with Pages Functions for analytics, the "Ask about Steven" assistant and Steven's private MCP server. In a browser with WebMCP, every page registers the same data and the assistant as tools (`src/webmcp.ts`, `ask_about_steven` in `src/ask/AskAssistant.tsx`). README.md has the full layout.

## Where the facts live

- `src/resume.ts` is the single source of truth for everything about Steven: `profile` (headline, summary, location, work authorization, availability, team size, contact), `experiences` (roles with stable `key`s), `impact` (the numbers on the home page, each with the role that `backing`s it), `skills`, `selectedWork`, `honors`, `education`, `languages`, `recommendations`, `news`. The site, the resume PDF, the MCP server and the site assistant all read it. Never hard-code a fact about Steven in a component.
- `public/steven-wilssens-resume-2026.pdf` is generated from `src/resume.ts` by `npm run resume:build`. Never edit or replace it by hand.
- `public/og-image.png` is generated by `node scripts/og-image.mjs` from `profile` and `public/profile.jpg`.

## When content changes

1. Edit `src/resume.ts` (and `src/pageMeta.ts` for a new page).
2. Run `npm run resume:build`. It renders the PDF, runs `scripts/resume-check.mjs` on the new and the current file (recruiter, ATS and editor checks: pages, extractable text, contact, headline, every role and date, bullets of the two latest roles, tense, scope, keywords, unexplained numbers) and only replaces the PDF when the score does not drop. The score is the ATS score: only the findings an applicant tracking system trips over (lens `ats`) count; the site and recruiter findings are listed beside it. Read its findings; fix the data, not the checker. `--force` exists for a deliberate trade-off and needs a reason in the commit message. The workflows compare the score with main (Site update) and with the live site (Deploy) and warn Steven in the pull request, the run and the emails when a change would lower it; `node scripts/resume-check.mjs --baseline https://steven.wilssens.com/resume-report.json` shows the same comparison locally.
3. `npm test` includes `src/resume.test.ts`, which fails when the PDF no longer matches `src/resume.ts`. Once live, the score of every résumé is recorded (`functions/_lib/resume-scores.ts`) and shown on `/admin` → **Résumé** with the findings, the questions and the history; a change to the checks shows up there too.
4. If the headline or photo changed, regenerate the share image.
5. `npm run lint`, `npm run test:coverage`, `npm run build`.

Do not invent facts or numbers. A number needs the role bullet that explains it (`impact[].backing`); a claim about an outcome needs a source (a recommendation, a public article) or Steven's own word recorded in the dossier. When a fact is missing, leave a `TODO(steven): …` comment and ask.

## Working on a branch

Feature branches, merged into `main` through a pull request with a merge commit (`gh pr merge --merge`) whose message says what changed for the reader (see `git log`). Nobody pushes to `main` directly; a pull request merges only when the required checks pass: `gates` and `team` (the Review workflow) and `check` (Site checks). Branch protection on `main` requiring exactly those three contexts is turned on by Steven once the Review workflow is on main; until he has, it is a rule the team keeps, not one GitHub enforces (`gh api repos/:owner/:repo/branches/main/protection` says which). Merging deploys to production; every other branch gets a preview at `https://<branch>.stevenwilssens.pages.dev`. Commit messages describe the change for Steven, not the diff.

## The team

Every change goes through Steven's product team (`.claude/team.md`): a senior product manager, a senior recruiter, a senior designer (UX), a senior developer, a senior security engineer and a senior tester, as agents in `.claude/agents/`. `/feature <ask>` runs the whole flow: spec in `specs/<slug>.md` (PM with the recruiter and the designer; security, test and engineering add their sections), Steven's open questions asked once, the build, the reviews in parallel by fresh agents, a fix loop, the pull request with the sign-offs. `/team-review [PR]` runs the gate alone on any branch or pull request; the Review workflow runs it on GitHub. The bars: coverage of 90% or more overall and per changed file (`npm run test:coverage`), and never worse for recruiters than main (`npm run check:recruiter`, the resume ATS score, and the recruiter's read of the pages). The designer checks the UI with `npm run screenshots -- <pages>`, against a build of main.

The team runs on Steven's money (the API key on GitHub, his Max plan's weekly limit in his sessions), so it does only the work a change needs. Only the reviewers whose part of the site changed review it (`scripts/review-roster.mjs`; a change to the rules, the team or the gates gets everyone but the recruiter, who only ever reviews résumé and website changes), and after a round only the ones that did not approve, or whose part changed since, review again. The developer and the security engineer run on Opus, the other four and the lead on Sonnet (the `model:` of each agent, `--model` in the workflows). A pull request opens as a draft while it is being worked on (the Review workflow skips drafts) and is marked ready once lint, the tests, coverage and the build pass locally, so GitHub reviews it once. Small changes (approved résumé proposals, a write-up refresh) take the short spec without spec agents.

The agent orchestration is part of the story `/building-this-site` tells (`src/articles/site/SiteArticle.tsx`, "The loop"). A change to it (a role added, removed or given a new bar, a new gate or check, a change to how `/feature`, `/team-review`, the Review workflow or the Site update workflow hand work between agents and Steven) updates that write-up in the same pull request: what the agents do, who signs off, what Steven still decides. The PM's spec lists it under the files to change and the PM's acceptance check fails without it. Numbers in the write-up still come from its feed, never typed in. `src/articles/sources.json` lists `.claude/team.md`, `.claude/agents`, the Review and the Site update workflows as sources of the write-up, and `building-notify.yml` starts one refresh a day when they (or a gate script) changed on main, so a change made without the write-up is still noticed.

Every explanation of how the agent workflow runs comes with a diagram (or several) that a reader gets at a glance: the write-up, the admin's Team page, `.claude/team.md` (a Mermaid chart GitHub renders) and a spec that changes the flow. A diagram changes with the flow it shows; prose without one is not finished.

Steven sees the team in `/admin#team`, generated at each build from the orchestration files (the list is `ORCHESTRATION` in `scripts/team-manifest.mjs`) and the first-parent history; nobody edits that page. Every change to those files reaches him there by itself as an unread update, like mail, until the Team page has been in front of him for 5 seconds; the line he reads is the merge commit's message (or the pull request title), so that message says what changed for him. A new kind of orchestration file goes into `ORCHESTRATION` (or `IGNORED`, with a reason) in the same pull request; `scripts/team-manifest.test.mjs` fails on a file that is in neither, and on any part of the real repository the generator cannot read. A change to `site-update.yml` counts only when its team step (`Let Claude make the change`) or the step that opens the pull request (`Open the pull request`) changes, and a change to this file only when this section (`## The team`) changes; the Team page shows this section as the team's rules. The page's diagram is the chart in `.claude/team.md`: every numbered step of `## The flow` has one `%% step N: <node>` line, and `class … you` / `class … gate` mark where Steven decides and where a change stops until it passes.

On GitHub: `gates` fails when the ATS score of the résumé drops below the live site's, or when the live site's report cannot be read, unless Steven himself puts the label `accept-lower-score` on the pull request (his deliberate trade-off; then re-run the job; a label added by anyone else, a workflow included, does not count). `team` fails while a reviewer asks for changes or waits for Steven (`NEEDS_STEVEN`); Steven answers by replying on the pull request, and the next Review run (a push, or re-running the job) passes the repository owner's replies (those nobody else edited last) to the reviewers as his decisions. A reply answers a question; it never clears a blocker. Dependabot's own pull requests (its branch, its commit) get `gates` only. The checkers come from main, the data from the pull request: after the pull request's own lint, tests and build, `gates` swaps in main's `scripts/recruiter-check.mjs` with `recruiter-compare.mjs`, `resume-check.mjs` with `resume-gate.mjs` (each pair only when main has both) and `functions/_lib/review/` and scores the pull request's `src/resume.ts`, PDF and pages; the team reviews by main's `CLAUDE.md` and `.claude/` (any other `CLAUDE.md`, `CLAUDE.local.md`, `.mcp.json` or `.claude/` folder is main's or removed). So a change to a checker or to the rules takes effect after it merges; the pull request that first adds them is checked by its own. Asks from the MCP and Building refreshes get the same flow inside the Site update workflow: the team writes `specs/<branch>.md` first and builds from it, and Steven's open questions land in the spec and the pull request.

Site update pull requests are pushed and opened by the site's GitHub App (installed on this repository only, Contents and Pull requests; never a personal token), from the workflow's `publish` job, which runs no branch code: it takes the change as a git bundle from the `update` job, where Claude and the team work with a read-only token, and refuses one that does not grow from main or touches `.github/`. Because the App's events start workflows, the required checks start on the pull request itself, like on anyone's. The commits, the pull request and the workflow's comments are the App's: nothing the App or a workflow writes counts as his (only the repository owner's `accept-lower-score` label and his own unedited replies do). When a change touches the assistant, the résumé or a write-up, the Review workflow runs the assistant check itself (five fixed questions, on the branch and on main, with the facts held to `profile`) and gives the answers to the recruiter; the preview has no assistant, no Turnstile and no MCP, so no reviewer asks Steven for a check it cannot run, and an assistant check that did not run is never a pass. When a required check did not start, `merge_site_update` with `recheck: true` closes and reopens the pull request so the checks start, as Steven. Merging stays his: `merge_site_update` with `confirm: true`, or his merge on GitHub.

## The admin

`/admin` (`src/admin/`) is laid out like the wilssens.com admin: a menu of pages chosen by the URL hash, an overview with **Needs you** and a tile per page, cards with `data-part` labels that become a chip bar, sortable and searchable tables (`DataTable`). A new part goes inside the right page as a `section.card` with `data-part`; something that waits for Steven goes in `needs.ts` so the overview and the menu badges show it.

## The Building write-ups

`/building-wilssens`, `/building-aibreaker`, `/building-this-site`, `/building-juniortrackcycling` and `/building-leo` (`src/articles/`) are refreshed from the projects themselves. `src/articles/sources.json` lists each project: its repository, the files that are its source of truth (CLAUDE.md first), and where its site answers the live numbers. After every push to a project's main branch, its "Building write-up" workflow tells this repository (`repository_dispatch`), the Site update workflow checks the project out, writes what changed into `sources/` (ignored by git), fetches the live numbers into the article's `feed.json`, and Claude Code updates the write-up where the files no longer agree with it; the result is a pull request like any other site update. The headline numbers of an article come from `feed.json` (the values at the last refresh) and, once the page loads, from `/api/building/<project>` (`functions/_lib/building.ts`: this site's own database, or the project's site). Never type a number that is in the feed into the article text. A project without an article (`"article": null`) is listed so its check-ins are noticed once the write-up exists.

## The MCP server

`functions/_lib/mcp/` is Steven's private workspace in Claude: it interviews him, keeps the dossier, reviews the site the way a recruiter would (`review_for_recruiters`), checks the resume (`check_resume`), compares LinkedIn (`save_linkedin_profile`, `compare_linkedin`), reads the traffic (`site_analytics`, over `functions/_lib/traffic.ts`), and asks GitHub to run the Site update workflow where Claude Code edits the site on a branch and opens a pull request (`request_site_update` carries several approved proposals at once, `wait_for_site_update` holds until the run ends, `site_update_status`, `merge_site_update` marks the proposals applied and explains or redoes a conflicted pull request, `close_site_update`). The site-update tools talk to Steven in plain English (`functions/_lib/mcp/plain.ts`): each update has a human name (`updateName`), every answer a `say` line without pull requests, runs or branches, and the ids stay in the other fields for chaining; `merge_site_update` takes the `sha` of the version Steven previewed and merges that commit or nothing, refuses an update still being checked or whose checks failed (named from the head commit's check runs), and redoes a real conflict on an `update/` branch by itself, once (as does `request_site_update` with `redo`). When an update is blocked, `site_update_status` and `merge_site_update` name what holds it from its own checks and the team's verdicts (the `team-verdicts` marker the Review workflow adds to its sign-off comment), and `merge_site_update` with `recheck: true` closes and reopens one whose checks did not start; a Building refresh is redone as a refresh (`repository_dispatch`). The workflow writes what it was asked into the pull request body as a hidden marker (`updateRequestFromBody` in `functions/_lib/github.ts`), with, for a Building refresh, the `project` and the `sourceSha` it was made from; keep the marker and the workflow inputs in step. Approved proposals the deployed résumé already carries are marked applied by `syncProposals` (`functions/_lib/mcp/proposals.ts`). Pure logic lives in `functions/_lib/review/` and `functions/_lib/mcp/proposals.ts` with tests next to it.
