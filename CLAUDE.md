# steven.wilssens.com

Steven Wilssens's resume site, read mostly by recruiters and hiring managers. React + TypeScript + Vite, prerendered to static HTML on Cloudflare Pages, with Pages Functions for analytics, the "Ask about Steven" assistant and Steven's private MCP server. In a browser with WebMCP, every page registers the same data and the assistant as tools (`src/webmcp.ts`, `ask_about_steven` in `src/ask/AskAssistant.tsx`). README.md has the full layout.

## Where the facts live

- `src/resume.ts` is the single source of truth for everything about Steven: `profile` (headline, summary, location, work authorization, availability, team size, contact), `experiences` (roles with stable `key`s), `impact` (the numbers on the home page, each with the role that `backing`s it), `skills`, `selectedWork`, `honors`, `education`, `languages`, `recommendations`, `news`. The site, the resume PDF, the MCP server and the site assistant all read it. Never hard-code a fact about Steven in a component.
- `public/steven-wilssens-resume-2026.pdf` is generated from `src/resume.ts` by `npm run resume:build`. Never edit or replace it by hand.
- `public/og-image.png` is generated by `node scripts/og-image.mjs` from `profile` and `public/profile.jpg`.

## When content changes

1. Edit `src/resume.ts` (and `src/pageMeta.ts` for a new page).
2. Run `npm run resume:build`. It renders the PDF, runs `scripts/resume-check.mjs` on the new and the current file (recruiter, ATS and editor checks: pages, extractable text, contact, headline, every role and date, bullets of the two latest roles, tense, scope, keywords, unexplained numbers) and only replaces the PDF when the score does not drop. The score is the ATS score: only the findings an applicant tracking system trips over (lens `ats`) count; the site and recruiter findings are listed beside it. Read its findings; fix the data, not the checker. `--force` exists for a deliberate trade-off and needs a reason in the commit message. The workflows compare the score with main (Site update) and with the live site (Deploy) and warn Steven in the pull request, the run and the emails when a change would lower it; `node scripts/resume-check.mjs --baseline https://steven.wilssens.com/resume-report.json` shows the same comparison locally.
3. `npm test` includes `src/resume.test.ts`, which fails when the PDF no longer matches `src/resume.ts`. Once live, the score of every résumé is recorded (`functions/_lib/resume-scores.ts`) and shown on `/admin` → **Résumé** with the findings, the questions and the history; a change to the checks shows up there too.
4. If the headline or photo changed, regenerate the share image.
5. `npm run lint`, `npm test`, `npm run build`.

Do not invent facts or numbers. A number needs the role bullet that explains it (`impact[].backing`); a claim about an outcome needs a source (a recommendation, a public article) or Steven's own word recorded in the dossier. When a fact is missing, leave a `TODO(steven): …` comment and ask.

## Working on a branch

Feature branches, merged into `main` with a merge commit whose message says what changed for the reader (see `git log`). Pushing `main` deploys to production; every other branch gets a preview at `https://<branch>.stevenwilssens.pages.dev`. Commit messages describe the change for Steven, not the diff.

## The admin

`/admin` (`src/admin/`) is laid out like the wilssens.com admin: a menu of pages chosen by the URL hash, an overview with **Needs you** and a tile per page, cards with `data-part` labels that become a chip bar, sortable and searchable tables (`DataTable`). A new part goes inside the right page as a `section.card` with `data-part`; something that waits for Steven goes in `needs.ts` so the overview and the menu badges show it.

## The Building write-ups

`/building-wilssens`, `/building-aibreaker`, `/building-this-site`, `/building-juniortrackcycling` and `/building-leo` (`src/articles/`) are refreshed from the projects themselves. `src/articles/sources.json` lists each project: its repository, the files that are its source of truth (CLAUDE.md first), and where its site answers the live numbers. After every push to a project's main branch, its "Building write-up" workflow tells this repository (`repository_dispatch`), the Site update workflow checks the project out, writes what changed into `sources/` (ignored by git), fetches the live numbers into the article's `feed.json`, and Claude Code updates the write-up where the files no longer agree with it; the result is a pull request like any other site update. The headline numbers of an article come from `feed.json` (the values at the last refresh) and, once the page loads, from `/api/building/<project>` (`functions/_lib/building.ts`: this site's own database, or the project's site). Never type a number that is in the feed into the article text. A project without an article (`"article": null`) is listed so its check-ins are noticed once the write-up exists.

## The MCP server

`functions/_lib/mcp/` is Steven's private workspace in Claude: it interviews him, keeps the dossier, reviews the site the way a recruiter would (`review_for_recruiters`), checks the resume (`check_resume`), compares LinkedIn (`save_linkedin_profile`, `compare_linkedin`), reads the traffic (`site_analytics`, over `functions/_lib/traffic.ts`), and asks GitHub to run the Site update workflow where Claude Code edits the site on a branch and opens a pull request (`request_site_update` carries several approved proposals at once, `wait_for_site_update` holds until the run ends, `site_update_status`, `merge_site_update` marks the proposals applied and explains or redoes a conflicted pull request, `close_site_update`). The workflow writes what it was asked into the pull request body as a hidden marker (`updateRequestFromBody` in `functions/_lib/github.ts`); keep the marker and the workflow inputs in step. Approved proposals the deployed résumé already carries are marked applied by `syncProposals` (`functions/_lib/mcp/proposals.ts`). Pure logic lives in `functions/_lib/review/` and `functions/_lib/mcp/proposals.ts` with tests next to it.
