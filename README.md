# steven.wilssens.com

Personal resume site for Steven Wilssens: a React + TypeScript + Vite single-page app hosted on Cloudflare Pages, with first-party, cookie-free analytics stored in Cloudflare D1.

- **Site:** https://steven.wilssens.com (https://stevenwilssens.pages.dev and every name under wilssens.net redirect to it)
- **Admin:** https://steven.wilssens.com/admin (token protected): visitors, the résumé score, the assistant, the career MCP, the agent team

## Development

```sh
npm install
npm run dev        # Vite dev server (analytics is disabled outside production builds)
npm test           # Vitest
npm run lint       # oxlint
npm run build      # type-check app + functions, build to dist/
```

To run the production build locally with the Pages Functions and a local D1 database:

```sh
npx wrangler d1 migrations apply stevenwilssens-analytics --local
printf 'ADMIN_TOKEN=local-test-token\nHASH_SALT=local-salt\n' > .dev.vars   # gitignored
npm run build && npx wrangler pages dev
```

Then check the built site against web best practices in a real browser (every public page
and every admin page, desktop and phone):

```sh
npm run check:site -- --token local-test-token
```

`scripts/site-check.mjs` starts its own `wrangler pages dev`, then on each page asserts the
layout (no sideways scroll; the admin has a single scroll container, its page pane), no
console errors or failed requests, the head tags search engines read, accessibility with
axe-core (serious and critical violations fail), and Lighthouse's accessibility, best-practices
and SEO scores (90 or more). It exits non-zero on a failure. The **Site checks** workflow
(`.github/workflows/site-check.yml`) runs it on every push, separate from Deploy so it never blocks
or hangs a deploy. The three write-ups' diagram accessibility backlog is reported as a warning
rather than a failure, so the gate still catches the admin, the core pages and any new regression.
`--lighthouse none` skips the Lighthouse pass, `--json <file>` writes the full report.

### Adding a page

Add the route to `routes` and its title/description to `pageMeta` in `src/pageMeta.ts`, then render it in `App.tsx`. The build creates the static HTML file and sitemap entry automatically.

### Updating the resume

The resume PDF is generated from `src/resume.ts`, the same data the site shows, so the two cannot drift:

```sh
npm run resume:build   # renders public/steven-wilssens-resume-2026.pdf in the installed Edge (or Playwright's Chromium)
npm run resume:check   # the analysis alone, on the current PDF
node scripts/og-image.mjs   # the 1200×630 share image, after a headline or photo change
```

`scripts/resume.mjs` renders an HTML resume to PDF, then runs `scripts/resume-check.mjs` on the new and the current file: pages, extractable text and glyphs, contact details, headline, every role and date, the bullets of the two latest roles, tense of past roles, team size, ATS keywords, numbers without a backing bullet, plus the questions the dates raise (gaps, overlaps). The score is the ATS score: 100 minus 25 per error and 5 per warning an applicant tracking system trips over (extractable text, contact details, section headings as lines of their own, the name first, every role with title, company and dates together and in the "Mon YYYY - Mon YYYY" form, education, keywords). Every finding carries a `lens`: `ats` findings make the score; `site` (the PDF differs from the data) and `recruiter` (tense, scope, numbers without a bullet) findings are listed beside it and do not change it. A new PDF only replaces the current one when its score does not drop (`--force` overrides). `src/resume.test.ts` fails when the PDF no longer matches the data, and the build writes the report to `dist/resume-report.json` for the MCP server's `check_resume`. Fix findings in the data, never in the PDF.

The score is kept on every update. The report carries the PDF's hash (`pdfHash`) and the commit it was built from; `functions/_lib/resume-scores.ts` records it in D1 (`resume_scores`, one row per PDF, migration 0009; the table is also created on first use) the first time a deploy serves a page (`functions/_middleware.ts`) and whenever `/admin` reads it. `/admin` → **Résumé** shows the score with the comparison to the résumé live before it, the findings, the questions the data raises, the proposals from the MCP, and the history of every résumé that went live with its score, findings and commit. `node scripts/resume-check.mjs --baseline <report.json or URL>` (or the `RESUME_BASELINE` environment variable) compares the resume with an earlier report and writes the comparison into the report. The Site update workflow scores main before Claude touches anything and compares afterwards: the pull request shows "Resume score: 90 → 85, lower than on main" with the new findings, a hidden marker lets the MCP server's `site_update_status` and `merge_site_update` warn Steven before a merge (he accepts with `acceptLowerScore`), and the email says so in its subject. The Deploy workflow compares every build with the live site's `/resume-report.json`, warns on the run when a branch would lower the score, and the "resume is live" email says whether the score went up, down or stayed.

## Ask about Steven: the assistant on the site

A floating "Ask about Steven" button on every page (and "Ask AI about my work" in the hero) opens a panel where recruiters and hiring managers ask anything about Steven's work. Built the way the help assistant on wilssens.com is:

- **Server** (`functions/_lib/ask/`): `POST /api/ask` streams an answer from Claude (`claude-opus-5-5`, effort low, server-side fallback on a refusal) as Server-Sent Events (`meta`, `delta`…, `done`). The system prompt (`prompt.ts`) is built from `src/resume.ts`, `src/patents.ts`, the **public** dossier entries and the three Building write-ups in full (read from their Markdown copies, `/building-*.md`, through the `ASSETS` binding, once per isolate), so the assistant knows only what Steven published; it is byte-stable and cached by the API for an hour. Every reply starts with a hidden first line the server strips: `[[in: role:csx-data, site:patents]]` (the sections it rests on, shown as links), `[[in: none]]` (in scope but not covered: saved to `ask_questions` as a gap) or `[[out]]` (off topic: our own fixed answer, the model's text is never shown). Answers are signed (HMAC with `HASH_SALT`) so the browser can send the conversation back and vote without forging an earlier answer.
- **Fit check**: a user turn marked `kind: 'fit'` is a pasted job description (up to 8000 characters; the model sees it behind the line `Job description to check against Steven's record:`). The prompt's fit-check rules make the answer a fixed shape: `**Covered**` (with the role or page that backs each requirement), `**Partly covered**`, `**Not shown on the site**` and `**Ask Steven**`, with up to six sources and more room (2200 tokens). The server reads the "Not shown" list (`missingRequirements`) and saves each requirement to `ask_questions` with reason `fit`, so a recruiter's unmatched requirement becomes a question for Steven; the posting itself is kept only as its length and first words (in `ask_log`). Text that is not a posting gets `[[out]]` and our own sentence (`words.notAPosting`).
- **Log**: every question goes to `ask_log` (migration 0012) with the analytics' daily visitor code (`functions/_lib/visitor.ts`), redacted, the answer beside it, kept 90 days; not on preview deployments, and nothing at all (not even `ask_questions`) when the browser sends Global Privacy Control or Do Not Track. `/admin` → **Ask about Steven** → **People who asked** counts the people (once a day, like visitors) and lists what each asked.
- **Limits**: 30 questions an hour per IP (salted hash, `ask_hits`), 1000-character questions (8000 for a job description), 12 turns and 30,000 characters per request (the panel sends the newest complete exchanges that fit with each question, so a conversation can go on; a request over the limit gets its own "start a new conversation" message), and a monthly budget (`ASK_BUDGET_USD`, default $25) counted from the API's token usage in `ask_daily`. A Turnstile human check (when `TURNSTILE_SECRET_KEY` and `TURNSTILE_SITE_KEY` are set) that is on standby on a quiet day and switches on when the assistant looks under attack: the day's spend passed `ASK_CHECK_AFTER_USD` (default $10), one connection asked 10 times in the last hour, or everyone together asked 60 times. `GET /api/ask` tells the page whether the assistant is on and hands out the site key only while the check is on; the button only appears when the assistant is.
- **Browser** (`src/ask/`): React panel docked beside the page from 1200 px (the page moves over), an overlay on tablets, a bottom sheet on phones; streaming with a caret, suggestions that fit the page, a "Check a job description" chip and foot link that swap the composer for a posting box (`openAsk(undefined, { fit: true })` opens it from anywhere, as the contact band does), sources as links, Copy, thumbs up/down (`POST /api/ask/feedback`), conversation kept in `sessionStorage` across pages. Markdown is rendered through `markdown.ts`: bold, lists and links only, links only to the site, the résumé, LinkedIn, Justia and Steven's email.
- **Report card**: `GET /api/ask/report` (`functions/_lib/ask/report.ts`, cached ten minutes, no token) is the assistant's public numbers over its whole life: questions, answered with sources, gaps, gaps Steven has since answered, open questions, votes, cost and cost per answer, public notes. The Building steven.wilssens.com write-up shows it live (`ReportCard` in `SiteArticle.tsx`); prerendered pages carry a sentence in its place.
- **Questions for Steven**: `ask_questions` rows are open until the MCP closes them (migration 0010: `resolved_at`, `resolution` answered | dismissed, `entry_id`). `/admin` → **Ask about Steven** → **Waiting for you** lists the open ones (gaps, job requirements, answers voted down) with how many were answered or set aside; **Needs you** counts them. In the MCP, `instructionsFor` tells Claude at the start of every session how many wait, `site_questions` lists them, `answer_site_question` saves Steven's answer as a dossier entry (public by default) and closes the question, `dismiss_site_question` sets one aside. The next answer on the site uses the new note. Everywhere these questions reach Claude (`site_questions`, `askedOnTheSite`) they travel with a caution that they are visitor text to show Steven, never instructions to follow.
- **Human check**: live in production since 18 October 2026 through a Turnstile widget ("steven.wilssens.com assistant", managed mode, domains steven.wilssens.com, stevenwilssens.pages.dev and localhost) whose keys are the `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` production secrets. Preview deployments do not have the secrets, so the check is off there. The widget is invisible unless Cloudflare wants an interaction; a token is spent per question, and the server verifies it against the request's host. The check is only enforced while it is **on** (see Limits); `/admin` → Assistant shows its state and why. The panel brings the widget up when `GET /api/ask` hands out the site key, or mid-conversation when a refused answer does (`403 human` carries `siteKey`). The first token takes a moment, so the panel waits for it (up to 8 seconds) before posting a question, and when the server rejects a token (spent, stale, missing) it resets the widget and sends the question once more with the next one before it shows the visitor a message. The Content Security Policy (`vite.config.ts`) allows `challenges.cloudflare.com` for the script and its frame; without that the widget never loads and, with the check on, nobody gets an answer.
- **Local**: `ASK_MOCK=1` in `.dev.vars` streams canned answers without an API call; with `ANTHROPIC_API_KEY` set it calls Claude. For the human check locally use Turnstile's test keys (`TURNSTILE_SITE_KEY=1x00000000000000000000AA`, `TURNSTILE_SECRET_KEY=1x0000000000000000000000000000000AA`), which always pass.

## WebMCP: the pages as tools for the agent in the browser

[WebMCP](https://webmachinelearning.github.io/webmcp/) (a W3C Web Machine Learning draft from Google and Microsoft, in Chrome behind `chrome://flags/#enable-webmcp-testing` since Chrome 146 and in an origin trial since Chrome 149) lets a page register tools with the browser, so an agent running in the browser (Gemini in Chrome, Copilot in Edge, or an extension) calls them instead of reading the DOM. Every page of this site does, from `src/webmcp.ts` (started in `main.tsx` like the analytics), and it sits on top of the assistant rather than the private MCP server: the tools return only what a visitor can see.

- **Data tools** (`src/webmcp.ts`, all read-only, built from `src/resume.ts` and `src/patents.ts`): `about_steven` (who he is, what he is looking for, location, authorization, availability, contact, the key numbers with the role behind each, skills, the role keys and page names the other tools take), `get_experience` (every role, or one by key), `get_selected_work`, `get_recommendations`, `get_patents_and_press`, and `read_site_page` (the Markdown copy of any page, `/about.md`…). Results are JSON text.
- **`ask_about_steven`** is registered by the panel (`src/ask/AskAssistant.tsx`) once `GET /api/ask` says the assistant is on, and runs through the panel's own send path: the panel opens, the visitor sees the agent's question and the streamed answer, and the limits, the Turnstile check and the votes apply exactly as for a typed question. The tool returns the answer, its scope and the sources as links; a question that arrives while another is streaming is turned away.
- **API shape**: the spec puts it on `document.modelContext.registerTool(tool, { signal })`, with the `AbortSignal` removing the tool; Chrome 146 to 149 had `navigator.modelContext` and `unregisterTool()`. `registerTool` in `src/webmcp.ts` handles both and does nothing in a browser without either, so nothing changes for everyone else. `llms.txt` mentions the tools for agents that read it first.
- **Try it**: Chrome with the flag on, then the [Model Context Tool Inspector](https://chromewebstore.google.com/search/Model%20Context%20Tool%20Inspector) extension lists the tools on any page and runs them, by hand or with a Gemini key. Tests: `src/webmcp.test.ts` and the WebMCP cases in `src/ask/AskAssistant.test.tsx`.
- **Reaching visitors on a stable browser**: the WebMCP origin trial (Chrome 149 to 162, extended to 30 March 2027, no approval needed; Edge runs its own with the same end date) turns the API on for every visitor of a registered origin. Register `https://steven.wilssens.com` at [developer.chrome.com/origintrials](https://developer.chrome.com/origintrials) (trial "WebMCP") and at [Microsoft Edge origin trials](https://developer.microsoft.com/en-us/microsoft-edge/origin-trials), paste each token into `originTrialTokens` in `src/pageMeta.ts`, and the build serves them as `Origin-Trial` headers on every page (`_headers`). Tokens are public and bound to the origin, so previews on `pages.dev` ignore them; when a token expires the tools simply stop appearing, so note the expiry date next to it.

## MCP server

One [Model Context Protocol](https://modelcontextprotocol.io) server (Streamable HTTP, stateless, JSON responses) in two modes, decided by `resolveMode` in `functions/_lib/mcp/server.ts`:

- **Owner**: `/mcp/<MCP_OWNER_KEY>` (or `/mcp` with the key as a bearer token) is Steven's private workspace. The link is shown on `/admin`. A wrong key is a 404, never a fallback to public.
- **Public**: `/mcp` without a key is a read-only server for recruiters, hiring managers and their AI assistants: `about_steven`, `get_resume`, `get_role`, `read_site_page`, `get_recommendations`, `get_patents_and_press`, `search_dossier` and `check_fit` (`publicToolNames` in `tools.ts`), over `publicView(store)`, which shows public dossier entries only and refuses every write. `check_fit` takes a job description and returns the whole published record (the same `dossierText` the site assistant uses) with the rules for an honest comparison, so the recruiter's own model does the work at no cost to us. `initialize` returns `publicInstructions`; a browser GET shows an explainer with the connector steps. 120 calls an hour per IP (the assistant's salted hash in `ask_hits`, `PUBLIC_CALLS_PER_HOUR`); beyond that a JSON-RPC error with HTTP 429. Every call is logged to `mcp_calls` (migration 0010: tool, query, country, network; no IP, kept 90 days) and shown on `/admin` → **Career MCP** → **Public server**, and `/api/mcp` returns it as `publicCalls`. The link is in the footer of every page, in the contact band on the home page, in the assistant's welcome, in `llms.txt` and in the Building steven.wilssens.com write-up.

Added to Claude (Settings → Connectors → Add custom connector) or Claude Code (`claude mcp add --transport http my-career <link>`), the owner mode is a workspace for talking through his career that builds on what is already there:

- **What is published**: `about_steven`, `read_site_page` (the Markdown copies of the site's pages that the build writes, including the three Building write-ups, read through the `ASSETS` binding), `get_role`, `get_recommendations`, `get_patents_and_press`, `get_resume` (the entries in `src/resume.ts`).
- **The dossier** (`dossier` table): facts and stories Steven records, one per entry, with a role key, topic, visibility and tags. `interview_status` shows which roles and topics are still empty and suggests questions; `save_entry`, `update_entry`, `delete_entry`, `list_entries`, `search_dossier`, `export_dossier` manage it. Entries are private by default; `public` means the assistant on the site and the public MCP server may use them.
- **Questions from the site**: `instructionsFor` adds a line at `initialize` when questions from the site assistant wait (gaps, job requirements a fit check could not match, answers voted down), `about_steven` repeats it, `site_questions` lists them with ids and what the assistant answered, `answer_site_question` saves Steven's answer as a dossier entry (public by default) and closes the question, `dismiss_site_question` sets one aside. Closed questions stay in `ask_questions` so the report card can count them.
- **The résumé** (`resume_proposals` table): at the end of a session Claude compares the dossier with `get_resume` and calls `propose_resume_change` for each concrete edit (exact current text, proposed text, why). A proposal can target any part of a role (`field`: title, company, dates, location, summary, or a bullet point), a whole role (`field: role`: add with `role: new-role` and the entry as JSON, replace, or remove), a section (headline, summary, skills, education) or the key achievements strip (`role: achievements`, the achievement as JSON `{value, label, backing}`; a number needs the role that backs it), so dates, titles, missing or obsolete roles and the numbers on the home page are handled the same way. Steven approves or rejects in the conversation (`review_resume_proposal`); `/admin` → **Résumé** and `list_resume_proposals` show what is approved or waiting. Approved changes go to the site through `request_site_update` (below) and are marked `applied` when that pull request merges. Independently of that, `syncProposals` (`functions/_lib/mcp/proposals.ts`) checks every approved proposal against the résumé data as deployed, each time the proposals are listed (in the MCP and in `/api/mcp`), and marks the ones the résumé already carries word for word as applied, so a change that went live through any pull request stops showing as approved.
- **The recruiter's seat** (`functions/_lib/review/`): `review_for_recruiters` reads the published pages, the resume report the build wrote and the LinkedIn import, and returns findings (what a recruiter trips over, why it matters, the fix: scope numbers, unexplained impact numbers, tense, gaps and overlaps, hiring logistics, proof from the wrong chapter, a resume that drifted from the site) plus the questions only Steven can answer. `check_resume` is the resume analysis on its own.
- **LinkedIn** (`linkedin_profile` table): LinkedIn has no API, so `save_linkedin_profile` takes the profile as text (LinkedIn → More → Save to PDF, or the page copied) or the CSV files of LinkedIn's data export (Profile, Positions, Skills, Education, Languages; the reliable route). `compare_linkedin` then lists, per difference, what LinkedIn says, what the site says, why a recruiter cares, and the exact text to paste into LinkedIn.
- **Changing the site** (`functions/_lib/github.ts`): `request_site_update` starts the **Site update** GitHub workflow (`.github/workflows/site-update.yml`), where Claude Code applies the brief on a branch (facts in `src/resume.ts`, `npm run resume:build`, lint, tests, build) and opens a pull request. One update can carry several approved proposals (`proposals: [ids]`; the brief is written from them by `briefFor`), which matters because every pull request regenerates the same résumé file and PDF, so two open at once conflict after the first merges. The workflow names its run after the title (so the tool returns the run it started) and writes two hidden markers into the pull request body: the résumé score before and after, and the request itself (title, instruction, proposal ids, the pull request it supersedes; base64 JSON, read by `updateRequestFromBody`). `wait_for_site_update` holds the call (up to 55 seconds, then says "still running") until a run finishes and returns its pull request (found by the run number at the end of its `update/<slug>-<number>` branch), preview link and score, so Claude does not have to poll, and its `outcome`: `pull-request`, `no-change` (the request was not carried out: the run failed at `Stop when no change was made`, with the run's reason quoted, and Claude offers Steven a redo), `failed` or `running`. `site_update_status` shows runs with their outcome and open pull requests with their preview links, the proposals they carry and `mergeTrouble` when GitHub cannot merge one. `merge_site_update` merges one into `main` (production), only with Steven's explicit confirmation, marks its proposals applied, and when the pull request conflicts with main says so and why; with `redo: true` (or `request_site_update` with `redo: <number>`) the same request runs again on a fresh branch and the workflow closes the old pull request with a pointer to the new one. `close_site_update` closes a superseded or unwanted pull request with a comment and deletes its branch. Needs the `GITHUB_TOKEN` Pages secret (a fine-grained token with Actions: write, Contents: write, Pull requests: write and Checks: read on this repository; without Checks: read a no-change run links to the run instead of quoting its reason; Contents: read is enough if closed branches may stay; `GITHUB_REPO` overrides the default `stewils/stevenwilssens.com`) and, in the repository's Actions secrets, `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` for Claude Code. The workflow uses the built-in `GITHUB_TOKEN` for everything else and dispatches the Deploy workflow for its branch itself, so the pull request gets a preview; the repository setting "Allow GitHub Actions to create and approve pull requests" must be on.
- **How the site is doing** (`functions/_lib/traffic.ts`): `site_analytics` returns the traffic the dashboard shows, compact: visitors and pageviews per day with crawler and AI requests beside them, résumé downloads and contact clicks, top pages, referrers and channels, countries and organizations, the crawlers by category (search, AI search, AI training, AI assistants fetching for a person) with the busiest bots and the pages they read, the assistant's questions and votes, and the public MCP server's calls, plus a `summary` in a few sentences (`describeTraffic`).

The server's `instructions` (in `functions/_lib/mcp/tools.ts`) tell Claude how to run a session: read what exists before asking, one question at a time, save as it goes, third-person entries, visibility rules, then the résumé proposals.

Local run: add `MCP_OWNER_KEY=<anything>` to `.dev.vars`, apply the migrations locally, then `npm run build && npx wrangler pages dev`. Tests: `functions/_lib/mcp/server.test.ts`.

## Deployment

Pushing to `main` runs lint, tests, and the build in GitHub Actions (`.github/workflows/deploy.yml`) and deploys to the `stevenwilssens` Cloudflare Pages project. Pull requests run the checks without deploying.

- The workflow needs the `CLOUDFLARE_API_TOKEN` repository secret (Cloudflare "Edit Cloudflare Workers" token template).
- Manual deploy: `npm run deploy` (requires `wrangler login`).
- `steven.wilssens.com` is a Pages custom domain, as are `steven.wilssens.net`, `www.wilssens.net` and `wilssens.net`: `functions/_middleware.ts` answers anything under `wilssens.net` with a 301 to the same path on `steven.wilssens.com` (`functions/_lib/hosts.ts`), so the old blog domain points at the current site. Both zones' DNS is on Cloudflare, each name a `CNAME → stevenwilssens.pages.dev`.
- Unknown paths return `404.html` with a 404 status.

## Analytics

Events are stored in the `stevenwilssens-analytics` D1 database (binding `DB`, see `wrangler.jsonc`). No cookies are used; a visitor is a SHA-256 hash of IP + user agent + `HASH_SALT` + the date, so visitors cannot be followed across days. Obvious bots are dropped from visitor stats; instead, `functions/_middleware.ts` records requests from search engines, AI crawlers and other bots in the `crawls` table (bot name, path, status, country, network; no IP), shown in the dashboard's Crawlers section. Signing in to `/admin` marks that browser to be excluded from tracking.

Pages Function secrets (set with `npx wrangler pages secret put <NAME> --project-name stevenwilssens`, then redeploy):

| Secret | Purpose |
|---|---|
| `ADMIN_TOKEN` | Password for `/admin` and its APIs (`/api/stats`, `/api/mcp`, `/api/ask/admin`, `/api/resume`, `/api/team`) |
| `HASH_SALT` | Secret salt for the daily visitor hash |
| `MCP_OWNER_KEY` | The key to the private MCP server at `/mcp/<MCP_OWNER_KEY>`; shown on `/admin` → **Career MCP**. Without it only the public read-only server at `/mcp` answers |
| `GITHUB_TOKEN` | Lets the MCP server start the Site update workflow and read runs and pull requests (fine-grained token: Actions write, Contents read, Pull requests write, Checks read) |
| `GITHUB_REPO` | Optional; defaults to `stewils/stevenwilssens.com` |

Repository Actions secrets (GitHub → Settings → Secrets and variables → Actions): `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` for Claude Code in the Site update workflow, and `MAIL_APP_PASSWORD`, a Zoho app password for steven@wilssens.com, so the workflows can email Steven when a pull request carries an updated resume (from the Site update workflow) and when a deploy to `main` changed the resume PDF or `src/resume.ts` (from the Deploy workflow). Without the password the steps print a notice and the workflows still pass. A mailbox in Zoho's EU data centre needs the repository variable `MAIL_SMTP_HOST=smtp.zoho.eu`.

The email itself comes from `scripts/resume-mail.mjs`: it loads `src/resume.ts` as it was before and after the change, lists every difference (a reworded bullet, a new role, changed dates, a dropped skill, a new key number…), and asks Claude to tell Steven in plain words what is different now (structured JSON output, so the headline, intro and items always come back in shape); the result is an HTML email in the site's colours with the recruiter score against the live site (or main), the findings when the score dropped, and the links (PDF, pull request, preview). It uses the `ANTHROPIC_API_KEY` repository secret the Site update workflow already has (`ANTHROPIC_MODEL` variable to pick a model; default `claude-opus-5-5`); without the key the email still goes out, with the changes listed from the data instead of written up. `node scripts/resume-mail.mjs live --before <commit> --after <commit> --report dist/resume-report.json --dry-run` writes the email to `resume-mail.html` and `resume-mail.txt` without sending; `scripts/send-mail.py` does the sending (plain text plus the HTML alternative).
